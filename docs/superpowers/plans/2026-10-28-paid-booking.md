**Goal:** Let a host optionally charge for existing appointments while preserving free booking, accepted Calendar continuity, and existing guest Wallet/Card approval.

**Architecture:** Extend the accepted Calendar command projection with host pricing policy and guest-specific reservation/payment phases. Compose existing Wallet Send and hosted Checkout through a scoped SQL gate/nonce wrapper that calls the unchanged transfer function; a dedicated existing Source-writer method retains progress across the file/SQL boundary. The same common server handler protects native and legacy booking, cancellation, confirmation, and delivery.

**Tech Stack:** Existing TypeScript/React Bank frontend, Next.js native routes, accepted file Action Ledger/Calendar Source, existing Wallet Send/Stripe deposit, service-only Postgres RPCs, Node tests, Vitest, and Playwright.

**Spec:** [Optional Paid Booking Specification](2026-10-28-paid-booking-spec.md).

## Global Constraints

- Existing appointments are free by default: `priceUsdCents = "0"`.
- The authoritative native price is an owner-authorized, accepted Calendar Source policy command. Native SQL settings are its projection.
- The appointment total is the host's saved price; `feeUsdCents = "0"` for this implementation.
- Positive prices are exact integer cents from `"1"` through `"10000000"`, matching the existing hosted Checkout amount ceiling.
- Only the accepted existing Wallet transfer and enclosing chat original, matched to the reservation and nonce, can confirm payment.
- Selected native Source failure is an error, never a switch to SQL Calendar.
- Account entry, Identity Seal behavior, first paint, ordinary Wallet Send, ordinary merchant checkout, and ordinary free host-created appointments remain unchanged.
- No live migration, credentials, payment, card deposit, production configuration, or identity mutation is part of plan preparation.
- This is a plan-only deliverable. Execution requires the main task's reviewed integration sequence. Do not stage, commit, overwrite another worker's dirty paths, or deploy as part of this plan.

## Review Focus

1. Two guests choose overlapping slots, including different start times/durations: only one reservation is accepted (Tasks 1–2).
2. A send reaches the database after host cancellation, expiry, or a process crash: the operation-wide gate prevents late charging/reassignment; an actual paid original wins (Tasks 2–4).
3. Payment or card deposit succeeds but its acknowledgement is lost: reopen the same approved nonce/event; deposit alone is not paid and unknown does not become zero (Tasks 3, 5).
4. Old/free clients, Twin proposals, query overrides, and absent booking descriptors attempt to bypass positive host price: backend and accepted Source admission reject them (Tasks 1, 3–4, 7).
5. Native Source/SQL projection disagreement, identity switching, or ambiguous email delivery occurs: stronger accepted truth remains visible; no fallback, cross-owner recovery, duplicate debit, or duplicate initial email (Tasks 3, 5–7).

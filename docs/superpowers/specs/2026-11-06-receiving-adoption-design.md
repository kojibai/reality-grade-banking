# Receiving and adoption

Approved direction: the holder is ready to pay; the recipient can receive, hold,
verify and use the money again. Bankeiz is an available receiving experience.
Receiz provides the existing proof infrastructure; Reality-Grade Banking is the
receiving standard. Keep the money first.

## Experience

- A collapsed **More receiving options** disclosure beside Wallet access opens
  a short explanation and **Help someone receive**, which opens the suite.
- One contextual sheet retains recipient, selected immutable UID, amount and
  optional purpose. It offers existing payment review or a reviewed invitation.
- Invitations use: “I’m ready to pay you. Here’s how to receive the money and use
  it for your next payment, with its proof and ownership intact.”
- Copy and native sharing happen only after preview. Amount and purpose are
  excluded unless selected. A prepared invitation is not a funded payment.
- A static `/receiving/` guide opens on phones without account data, with
  discoverability through Guides and the shared footer. Send remains in place. Reviewed
  invitation text is carried in the URL fragment, parsed locally and removed
  from the address. It never enters public caches, metadata or server requests.
- A direct route opens existing Bankeiz receiving. Institution guidance opens
  the standard, kit, applicable checks, assessment and existing Registry.
- Registry records offer **Bring the standard to your institution**, preserving
  the actual institution and evidence scope. An unlisted name implies no consent.
- Conformance offers preparation before a credential exists, retaining every
  existing workspace, assessment and publication guard.
- A collapsed private **Receiving invitations** list inside the optional receiving
  sheet retains drafts,
  copied/share-initiated facts and explicitly participant-reported responses.
  Reopening a draft offers normal payment review; it never submits payment.

## Boundaries

Reuse installed SDK/MCP/AI v129 and existing account entry, wallet executor,
receiving, encrypted identity-bound local storage, navigation and Registry.
No dependencies, new identity/account, balance, ledger, standard or Registry.
No capability discovery on entry, background polling or duplicate reads.
Opening help is synchronous. Private work loads only on explicit draft/list use.
No public preview contains recipient email/UID, draft IDs or account balances.
Sharing initiated is not delivery. A scoped PASS is not a receiving route or a
recipient's willingness. Exact recipient/funding/authority checks stay in the
existing payment review and execution. No real outreach or funds during QA.

## Approach

Connect the existing product with one small local coordination layer and public
guide. A separate adoption application would duplicate navigation and context;
automatic routing/discovery would introduce requests and unsupported readiness
claims. The approved contextual approach preserves the working experience.

Final presentation refinement: More receiving options is a collapsed disclosure beside Wallet access, using the exact same disclosure styling. Opening it reveals a short explanation and Help someone receive. Only that explicit action opens the suite; expanding the disclosure performs no read.

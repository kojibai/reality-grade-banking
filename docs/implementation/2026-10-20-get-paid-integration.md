# Get paid: existing Receiz v129 integration audit

Source audit, 2026-10-20. This is queued work after the asset/history work. No payment, private query, checkout/status lookup, financial SDK/MCP call, host edit, or production qualification was performed. Installed `@receiz/sdk` and `@receiz/ai-skills` are 129.0.0. References below identify implemented source contracts, not demonstrated live support.

## Recommendation

Keep Receive as the entry point and reuse the existing account, payment, Note, and proof readers. Add Get paid, share link, website button, and developer instructions as presentations of those same rails. Do not create another merchant balance, money store, credit writer, or settlement service.

Three current limitations must be resolved before advertising one checkout that accepts cards, account money, and every Bank Note:

1. **The public embed's Note uploader is legacy token-only.** It extracts a `note_…` token and calls `wallet_claim_note`. Modern Bank Reserve, Settlement, and composite Notes carry signed funding/handover sources, a bound receiver, and a separately signed claim. They cannot be assumed claimable through this uploader. The installed SDK support map explicitly preserves that distinction.
2. **Arbitrary merchant card iframes are blocked by the current host policy.** Receiz `proxy.ts:467` and `:622` enforce checkout `frame-ancestors` of self, `https://bankeiz.com`, `https://bank.receiz.com`, and the fixed 4173/5173 loopback addresses. The existing public widget creates `/payments/embed/checkout` directly in the merchant page. Its advertised paste-anywhere card experience therefore needs a host-policy decision and real qualification. CORS permission does not override frame ancestors. A normal link to a hosted payment page avoids the framing issue.
3. **Modern connected Note transport is Bank-specific.** `bankNotes/attestationRealm.ts` admits only the two existing Bank registered clients and their approved origins. A newly registered merchant app does not gain this transport merely by requesting Reserve/Settlement scopes. Do not document a nonexistent generic SDK Note checkout method or bypass the realm check.

## Card inputs, results, and completion

The public create body accepts `username`, `amountUsd`, optional `currency: "usd"`, `uiMode: "embedded" | "hosted"`, `successUrl`, `cancelUrl`, `returnUrl`, `referenceId`, `description`, `customerEmail`, and compact metadata. It currently allows $0.50–$100,000, bounds JSON at 32 KB, and applies IP limits (defaults 24/minute and 240/hour; deployment environment may alter them).

The actual response is nested, despite the SDK's broad `CheckoutSessionResponse` type:

- `merchant: {username, displayName}`;
- `checkout: {mode, sessionId, amountUsdCents, currency, referenceId, statusPath}`;
- embedded adds `clientSecret`; hosted adds `url`.

Validate the returned merchant, exact integer cents, currency, session ID, mode, and expected origin before presenting checkout. Reuse `ReceizCardCheckout`'s existing fragment/bootstrap and iframe boundary for Bank-hosted presentation, adapting its consumer's purpose rather than changing financial behavior. Its guarded Bank message listener is a stronger integration example than trusting arbitrary widget messages.

The public status result contains `session: {sessionId, state, isPaid, isTerminal, stripeStatus, stripePaymentStatus, merchantUsername}` and an optional settlement summary `{kind,userId,amountUsdCents,amountPhiMicro,alreadyProcessed}`. States are `open`, `paid`, `complete_unpaid`, `expired`, `unknown`; only `isPaid === true` is provider-paid. The public status projection does not include the complete amount/account proof needed by Bank admission. Verify the merchant's actual credited account source/history before declaring money received. The delegated status adds exact amount/currency/reference fields and account/client binding.

Both status routes call `settlePaidStripeWalletCheckout` for paid sessions. The Stripe webhook also uses that writer. When a native account source is selected, `walletSettlement.ts` requires the selected funded wallet source and appends admitted funded credit; it refuses a missing funded source rather than falling back to legacy SQL. Compatibility selection is an existing host responsibility. Card receipts represent Reserve credit; they do not themselves execute an account transfer, buy an asset, or admit Note custody.

The create routes do not pass a Stripe idempotency key or expose a create-by-reference recovery lookup. `referenceId` is metadata, not demonstrated create idempotency. Retain a known session before navigation and resume/check that session. An unknown lost create response must remain unresolved rather than blindly creating a second session. Receiver credit deduplication by the existing writer does not deduplicate two separately paid sessions.

## Modern Notes: preserve the existing path

Bank currently enables connected issuance and keeps protected continuous-offline prepared credit disabled. `selectNoteFunding` preserves exact Reserve backing, uses Settlement only for the remaining denomination, and records `fundingParts` for `composite`. Never flatten that into one legacy token claim or recompute the carried split at the current rate.

Existing sequence:

1. Recipient creates a signed account receiving request using `createBankNoteAccountReceivingRequest` through the pinned Bank Note module. This is a receiving statement, not a private key or authorization to credit a different account.
2. Sender opens the exact funded Note source and uses `createBankConnectedNoteHandover` with that request and the Note's signing custody. The handover binds receiver user ID/key ID, funding digest, and request digest. The existing Bank `offlineNotes.transfer` retains the exact request and same attempt.
3. Recipient opens the complete source, requires `kind === "handover"` and matching receiver account/key, then calls `createBankConnectedNoteClaim`. Bank retains `{action:"claim", claim, source:<base64url exact source>}` before submission.
4. `POST /api/connect/offline-notes/connected?origin=…` accepts exactly those fields. Recover an uncertain claim with `GET …&noteId=<uuid>`; recover issue with `GET …&allocationId=<64-hex>`; quote is `GET …&intent=quote`. The existing issue/cancel bodies are exactly `{action,authorization}`.
5. Response supplies base64url `source` and **private** `privateAccountOpening`, with `found` and optional `cancelled`. `verifyBankConnectedNoteCredit` must validate signatures, receiver, exact terminal source digest, claim/redemption digest, amounts, rail, both funding parts, and resulting account opening. Only then reconcile the existing received-Note queue and account history.

The host requires `receiz:wallet.read`, the admitted Bank client/origin realm, and the corresponding `receiz:reserve.write` or `receiz:settlement.write`; composite requires both. The service reuses the selected native writer; a selected failure cannot install a second Note wallet or switch to SQL. Arbitrary sites cannot obtain these privileges from wildcard CORS.

**Missing merchant capability:** a supported way to publish/resolve a nonsecret, merchant-bound receiving request; a delivery/notification path for the complete receiver-bound handover; and merchant-side claim admission/recovery in an authorized receiver runtime. The current legacy embed performs none of these. Initially hand off to the existing Bank Note receiver UI; do not make anonymous third-party JavaScript hold the merchant's identity, account opening, or signing custody. A later Receiz host extension may expose the same native primitives under an explicit merchant contract, but must not create a new credit writer.

## CORS, frame, callback, and event policy

- Public embed APIs use `Access-Control-Allow-Origin: *`, no credential allowance, fixed allowed headers, and `POST, OPTIONS` (`GET, OPTIONS` for status). Widget requests use `mode:"cors", credentials:"omit"`. Public merchant resolution rejects private/missing profiles and uses the selected native account profile source when present.
- Public create callback origins are the Receiz app origin, the request Origin/Referer origin, and `RECEIZ_PAYMENT_CALLBACK_ALLOWED_ORIGINS`. Delegated create uses Receiz plus registered client redirect origins and that environment list. Callback URLs must be HTTPS, except `http://localhost`; arbitrary `http://127.0.0.1` is not accepted by this helper. A callback's presence is not settlement evidence.
- The checkout child posts `checkout-ready`, `checkout-complete`, and `checkout-error` to `"*"`; the widget checks source window and a supplied session ID, but does not check `event.origin`. Its Stripe `onComplete` also emits completion without the completion-only page's status lookup. A new integration must check the exact Receiz origin, exact iframe window, required exact retained session ID, and then verify status/credit independently. Do not grant fulfillment from `postMessage` alone.
- The legacy widget places its client secret in **both query and fragment**, and also `window.name`; Bank's existing checkout component uses a fragment and `referrerPolicy="no-referrer"`. Do not copy the query-secret pattern into the new Bank presentation, logs, analytics, share links, or exports. Return URLs should carry only a resumable session coordinate, never signing/claim secrets.
- Third-party builder requirements are real: script/custom-code permission, site CSP `script-src`/`connect-src` for Receiz, approved checkout framing and Stripe prerequisites, public HTTPS, and a correctly resolved public merchant username. A plain payment-link `<a>` needs none of those scripting/CORS permissions. No new developer/OIDC registration is required merely to emit the existing public username snippet; an authorized developer integration does require its own registration.

## Later Note QR/status work

Existing **legacy** paths are `/wallet/note/<noteId>/status/<proof>` and `GET /api/wallet/notes/status/<noteId>/<proof>`. The proof is SHA-256/base64url of `receiz_wallet_note_status_v1:<id>:<legacy noteToken>`, and the reader looks in `wallet_notes`. A logged-in POST to the same API path plus `/claim` can retrieve the token internally and claim; therefore this status URL is not necessarily a harmless public read-only identifier. Do not reuse it as a modern Note's generic QR or publish it indiscriminately.

The legacy status exposes minted/claimed/void status, amount, dates/pulses, `heldBound`, optional current-holder metadata, and an explicitly unpublished ownership projection. It does not guarantee a verified claimant name. Held-bound claim attempts are refused. Modern connected Notes carry different sources and no legacy token; no connected-Note public status/claim-page reader was found in these paths. Bank's current `note-artwork.ts` adds no QR.

After current work, design a separate nonsecret status locator bound to the immutable Note/source identity. Derive issue/accepted-claim times and rail from the existing verified funding/credit sources, clearly distinguishing local received, pending online reconciliation, and credited. Keep public status availability distinct from the last verified source. Disclose an account's public Receiz ID only under an established public identity/disclosure rule; never reveal private account openings, balances, tokens, or signing material. A QR scan may open status and the already admitted receiver workflow; it must not transfer by scanning, substitute a new recipient, or claim through legacy SQL.

## Proposed implementation order and release evidence

1. **After assets/history:** add a Get paid section within existing Receive. Reuse its prepared public receiving username and optional exact amount. Keep existing account-money link sharing. Offer the existing Receiz merchant link and explain supported methods accurately. Confirm the public merchant resolver recognizes the current Bank account; a username string or a copied snippet alone is not merchant setup completion.
2. **No-code first increment:** generate an ordinary styled anchor to the current appropriate hosted link, with no secret/token embedded. Existing Bank link = account-money review; existing Receiz link = current card/legacy-Note widget. Do not claim one universal checkout yet. A future Bank-hosted public pay route can present all supported methods while reusing these same financial operations; that route is proposed, not currently implemented.
3. **In-page checkout:** qualify the current Bank approved iframe path first. Resolve arbitrary merchant framing through the Receiz host's explicit allowed-origin contract, or keep hosted navigation. Do not widen frame ancestors implicitly from Bank UI.
4. **Modern Notes:** add the merchant receiving-request/delivery/claim contract around existing native primitives, preserving receiver custody and the Bank realm policy until an explicit host change is authorized. Keep legacy Notes clearly labeled; do not route modern images into token extraction.
5. **Developer guide:** publish separate examples for unsigned `payments.embeddedCheckout`, merchant-authenticated `connect.checkout`/`checkoutSession`, existing `connect.transfer`, and the current Bank Note receiver composition. Pin v129; show nested response validation, genuine user consent, exact application ID, PKCE or proof-authority/source/session prerequisites where applicable, minimum scopes, unknown-outcome recovery, and proof admission. Modern registered clients must qualify actual operations and deployed dependencies. Historical `merchants.*` / broader `commerce.*` interfaces require an explicit compatible host and must not be presented as default Receiz capabilities. `commerce.oneClickCheckout` returns `wallet_settlement_execution_required` with zero applied wallet money when funds would be used.
6. **Only later:** issuance QR/status presentation, following the privacy boundary above.

Before any live-support claim, demonstrate with authorized accounts: public merchant resolution; actual card payment and exactly one admitted Reserve credit after redirect/reload/webhook retry; exact account-money payment and receiver credit; Reserve, Settlement, and composite Note handover/claim/recovery; duplicate/lost-response cases; receiver/key/origin mismatch zero-write rejection; public/private identity disclosure; and real desktop/mobile merchant-site framing. A fixture, callable method, source test, generated registration, or successful card-session creation establishes none of these live outcomes.
